# D-002：单一主体与唯一认知提交

## 背景

多个会话、模型、工具和离线任务可能同时产生状态候选。如果每个模块独立修改人格、关系、记忆和生活事实，系统会形成多个相互竞争的主体。

## 当前选择

一个 Heptalogos 实例维护一个核心主体。多个任务可以并发读取和计算，但关键主体状态、对外行为和自我陈述由一个 Cognitive Commit Coordinator 或等价的串行化机制统一提交。

## 原因

- 保持“同一个主体”；
- 避免跨会话共享状态被静默覆盖；
- 保证状态变化和 ActionPlan 使用同一快照；
- 允许集中执行隐私、权限、知识和叙事审查；
- 提供清晰的 Trace 和冲突重算语义。

## 不意味着

- 所有代码只能单线程；
- 模型调用不能并发；
- 长工具必须阻塞认知；
- 每个会话不能独立维护 Mailbox；
- 不能使用子 Agent。

并发工作只提交候选或结果事件，不直接写共享主体状态。

## 代价

- 需要 Job 调度、快照版本和提交冲突处理；
- 长认知事务可能造成排队；
- 必须将长工具移出提交临界区。

## 重新考虑条件

如果未来一个部署需要维护多个相互独立的主体，应为每个主体建立独立提交分区，而不是让同一主体存在多个写入者。
