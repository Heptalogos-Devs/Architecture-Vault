# 引导、稀疏覆盖与真实生效

[nous.bootstrap.toml](安装配置/nous.bootstrap.toml)按正式Bootstrap类型给出外部PG安装。urlRef是安装所有者在受保护bootstrap secret binding登记的`database-url`，内容是该安装的PG连接信息；示例不包含凭据。首次init由实际owner生成installationId，复制示例时不能让多个新安装使用相同身份。Hept使用自己的安装身份和库，product改hept、默认端口8788，其余沿同合同。

程序运行与可选依赖根由env-paths或明确locator补齐。实验时把实例locator放在工作区temp下，所有相对数据/缓存/日志也留在temp；已有正式实例不要指向这个临时位置。bootstrap不自动启动Subject或调用模型。

## 一次不污染继承的修改

[network-change.json](安装配置/network-change.json)是空安装初次修改的完整SettingsChange。必须先创建本层缺失的父JSON对象，再add叶字段；成熟RFC6902实现不会为`/profiles/default/timeout/connectMs`自动创建父节点。管理入口调用`settings.read(ctx,{namespaces:['platform.network'],scope})`，同一次读取从`targetOverrides['platform.network']`取得本层`sparse`和`revision`，从`modules['platform.network']`取得有效值与来源。更改已有稀疏对象时只添加缺失父节点，不用空对象覆盖既有值；提交的`expectedRevision`使用该目标覆盖修订。

提交方式为PATCH /v1/settings，Idempotency-Key取一次稳定submissionId。body不重复submissionId或Actor。该示例只保存：

```json
{"profiles":{"default":{"timeout":{"connectMs":8000}}}}
```

产品defaults补齐profile中的代理/TLS/其他超时等字段。schema本身没有default副作用；原Zod带default对象.partial()的空修改路径退出。读取结果带定义修订、安装revision和每字段来源。

已保存revision为1时，用下一次稳定提交恢复继承：

```json
{
  "namespace":"platform.network",
  "scope":{"kind":"installation","installationId":"019c8000-0000-7000-8000-000000000001"},
  "expectedRevision":1,
  "paths":["/profiles/default/timeout/connectMs"]
}
```

该输入发送POST /v1/settings/reset；删除覆盖后下次连接回到产品默认10000ms。删除路径留下的空对象按JSON对象合并，不会再遮住默认值。冲突先返回当前修订，不覆盖另一操作者。重复同一提交返回原owner结果，不能因当前head已变而执行第二次修改。

## 数组、限制与生效

同一profile的`tls.caFileRefs`是数组，某层显式设置就整项替换，不按索引拼接；reset清除本层值后恢复上层数组。新的CA或代理只有安装权限可配置；Subject/Role的局部覆盖不能放宽机器网络访问和预算上限。

保存与生效分开：本次写事务只保存修订/回执并通知，随后网络owner为新请求创建对应revision的池，旧调用保留原快照；界面显示saved/applied差别。修改Role参数、Prompt和网络后，下次真实模型调用的InvocationSnapshot应指向实际采用的配置/Prompt修订及profile。预览和配置编辑本身不产生模型费用或Subject经历。

完整字段、默认、四层scope与SQL见[配置](../设计/基础设施/配置与生效.md)、[网络](../设计/基础设施/网络与外部资源.md)、[安装](../设计/基础设施/安装与生命周期.md)。
