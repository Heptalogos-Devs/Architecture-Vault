# IM 交互场景

## S-01 连续补充

用户发送：“我明天去北京” → “不是出差” → “去见朋友”。系统应等待短窗口，将三条视为一个观察批次，而不是连续回复三次。

## S-02 中途撤回

用户发送敏感内容后撤回。若回复尚未发送，应取消或重新规划；长期记忆不应仅凭已撤回内容形成稳定事实。

## S-03 引用旧消息

用户引用两小时前的一张图片问“这个你还记得吗”。系统应解析引用关系、等待媒体分析结果，并优先使用该消息链而非最近话题。

## S-04 群聊旁观

多人讨论技术问题但未直接询问 Agent。系统根据参与历史、信息价值和频率预算决定沉默、表情反应或简短补充。

## S-05 群聊点名后被他人打断

Agent 被 @ 后开始生成，期间另一成员提供了正确答案。系统应检测回复价值下降，取消或改成确认/补充。

## S-06 私聊关系不泄露

用户在私聊中透露健康或情感信息。群聊中出现相关话题时，系统不得引用该私聊记忆。

## S-07 记忆纠正

用户说“我已经不吃素了”。系统应保留旧信息的历史有效期，将当前偏好更新为非素食，并避免继续使用旧偏好。

## S-08 模糊关系推断

用户连续几天聊天不等于关系自动升级。系统可以更新互动统计，但亲密度等抽象关系状态需要更严格证据或上限。

## S-09 异步工具完成

用户让 Agent 深度搜索后离开。任务完成事件到达时，系统根据当前会话、安静时段和用户设置决定立即通知、延后或等待用户回来。

## S-10 主动承诺

Agent 曾明确承诺“明天提醒你提交申请”。这应形成持久承诺和唤醒任务；重启后仍可履行。

## S-11 工具失败

日历工具超时。Agent 不得声称已创建日程，应说明当前未完成，并依据策略重试或询问用户。

## S-12 多平台同一人物

同一人物在 Telegram 继续 QQ 中的话题。系统需要识别身份绑定和共享范围，但不得假定所有平台账号天然属于同一人。

## S-13 机器人被禁言

平台禁言事件改变输出能力。系统仍可记录和形成计划，但必须明确暂停投递并处理过期。

## S-14 高流量群聊

一分钟数百条消息时，系统应背压、抽样或主题聚合，不得为每条消息创建独立主模型请求。

## S-15 用户关闭主动行为

关闭后，环境变化和任务完成仍可记录，但不得产生未请求的主动消息，除非属于用户明确设置的提醒。
