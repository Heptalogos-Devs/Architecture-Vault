## 二、已核实的配置默认值问题

本机实际 Zod 为 4.6.5。用其直接运行：

```ts
const schema = z.object({ n: z.number().default(7), flag: z.boolean().default(true) });
schema.partial().parse({});       // { n: 7, flag: true }
schema.partial().parse({ n: 3 }); // { n: 3, flag: true }
```

当前重建 `SettingsPatchSchema` 从带默认值的 schema 派生 `.partial()`，空修改会变成显式默认覆盖。后层保存一次局部修改就可能改变上层其他值。独立的无默认输入保留空对象。

选择：模块约束 schema 与产品 defaults 分开；修改作用于本层稀疏覆盖，先合并所有覆盖，最后一次补默认并验证。通用 JSON Patch、对象合并直接采用成熟库，不维护一个访问 Zod 私有 AST 的 deep-partial/default-removal 生成器。实验脚本位于 `temp/spec-research/probes/config-defaults.mjs`。

## 三、网络版本组合的实际行为

本机 Node 24.21.0 内置 Undici 7.29.1。研究下载 Undici 8.10.0，源码 commit `c8d80e6b2dcfab282557b08f51352937bc9e5692`，要求 Node >=22.19.0，无额外运行依赖，MIT。它直接提供 HTTP/环境代理与 Socks5ProxyAgent。

跨代 Fetch 对象存在实际差异：

| 本地实际组合 | 结果 |
|---|---|
| Node 原生 FormData → Undici 8 fetch | 请求返回 200，但 body 没有 multipart 字段 |
| Undici 8 Agent → Node 原生 fetch | invalid onRequestStart / UND_ERR_INVALID_ARG |
| Node 原生 Request → Undici 8 fetch | Invalid URL |
| Node 原生 Request/FormData/fetch + 官方 Dispatcher1Wrapper(Agent8) | 原始字段和 multipart 完整到达 |
| 同版 Undici 8 fetch + Web ReadableStream | 流式上传完整到达 |

采用 Node 的 WHATWG Request/Response/Headers/FormData/fetch，Dispatcher 8 通过其官方 `Dispatcher1Wrapper` 接到 Node 24；不编写私有 Fetch 对象转换。每个资源取得独立的 Dispatcher 策略，避免安装级全局替换影响其他 SDK。[官方兼容实现](https://github.com/nodejs/undici/blob/c8d80e6b2dcfab282557b08f51352937bc9e5692/lib/dispatcher/dispatcher1-wrapper.js)、[迁移说明](https://github.com/nodejs/undici/blob/c8d80e6b2dcfab282557b08f51352937bc9e5692/docs/docs/best-practices/migrating-from-v7-to-v8.md)。实验脚本与输出是 `network-multipart.mjs` / `.json`，只连接本机临时 HTTP 服务。

因此可直接使用 Agent、EnvHttpProxyAgent、ProxyAgent、Socks5ProxyAgent、连接/TLS/流控能力。SDK 原生 multipart、ReadableStream、取消与请求对象仍完整保留。具体网络授权属于产品的资源范围；模型、Web、媒体、渠道和原生浏览器各消费自己的策略。

## 四、持久执行与普通事务

已安装 DBOS 5.3 的 Kysely datasource 正式提供 `client`、`runTransaction` 与 `registerTransaction`；业务写入与事务检查点可在同一次数据库事务提交。普通 Kysely 事务仍适合无需持久执行的短操作。[官方事务接口](https://docs.dbos.dev/typescript/tutorials/transaction-tutorial)。

官方 `@dbos-inc/vercel-ai` 0.5.4 实际源码还表明：

- `durableCalls` 在 workflow 内用 `DBOS.runStep` 保存每次 provider 结果；在 workflow 外直接调用。
- 明确拒绝在数据库事务内调用模型。
- 同一 workflow 中并发 durable model call 会因重放顺序不确定而拒绝；需要并行时用独立子 workflow。
- 流式结果会先持久完成，再向下游发 finish；取消、abort 与 workflow cancellation 各有实际语义。
- 请求/响应 raw body 默认不进入检查点；必要时由明确 include 选择，普通诊断无需复制一套完整请求档案。
- 单靠 checkpoint 不能消除 provider 已执行但结果尚未保存的窗口；真实调用 owner 需要保留 invocation 身份与 unknown，结合 provider 的实际幂等/查询能力处理。

当前 createNous 把大部分短操作统一注册为 workflow，且用固定 applicationVersion。应缩回真正的长工作、持久等待和外部执行，不让每个简单资料读取/创建都变成工作流平台操作。DBOS 提供运行进度；业务只保存模型调用和实际效果的领域事实，不另建通用 step/lease/outbox 系统。

## 五、共享代码与产品独立性

选择发布普通库 `@nous-wave/platform`，源码置 Nous 仓库 `packages/platform`，按 settings/network/models/prompts/credentials/telemetry/storage 等独立 export。它组合成熟依赖和必要的通用资源机械，各产品创建独立实例、独立数据库与注册定义。库中没有 Memory、World、Reactor 或两边业务状态。

这让相同配置求值、网络客户端、Prompt 资源、模型供应与诊断接线只维护一处，同时保持两个服务独立。Hept 使用正式 npm/tarball 发行依赖；当前 `packages/hept/package.json` 中相邻 Nous `link:` 依赖必须替换。库和 SDK 均以普通 ESM 及声明文件独立构建。

领域内容和授权由产品 owner 决定：Prompt 正文归角色，世界时间映射归 Hept，认知查询与认识状态归 Nous。共享库不增设总管、动态业务平台或常驻第三服务。

## 六、研究形成的规划

基于上述事实，已在[基础设施详规](https://github.com/Heptalogos-Devs/Architecture-Vault/blob/60122d8f4d10e867b47ad14fea2b119274ce473f/设计/基础设施/README.md)确定目录与三种生命周期、配置字段/修订/生效、模型多能力、Prompt资源、网络范围、数据库/Blob/缓存、时间、身份、诊断、公开入口和数据恢复。各专题写明采用文件/API及领域消费者；[施工顺序](../施工顺序.md)将最小real capture与Blob保全放在首个模型调用之前，完整虚拟时间和复杂媒体随后接入。

当前研究没有运行两个产品服务、付费模型或实际平台账号。网络/默认值/时间/消息的少量隔离实验用于判定接口与依赖组合，正式集成场景安排在底座施工单元。
