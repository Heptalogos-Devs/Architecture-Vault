# 身份、权限与密钥

使用[共同值与调用上下文](共同值与调用上下文.md)的 SubjectId、Ref、OriginIdentity、Consumer、Actor、CallContext、Policy 和 trace。本规范给出授权、委派与秘密的实际规则；权限不放在模型自报字段中。正常产品管理、主体行为、后台专业执行及本机恢复各有独立入口。

## 1. 采用方式与责任

Better Auth 及正式 admin/API key 插件直接承担账号、密码、会话、API key 校验、过期和限速。产品 Identity/Management 持有 Subject、服务委派、账号连接与具体目标范围。共享普通库 `@nous-wave/platform/credentials` 组合已选成熟 OS/keyring、环境和受保护文件能力，每个产品单独实例；它不持有所有产品的用户与业务权限。

原 Hept 权限和 Secret 源码已经复制到 `temp/spec-research/source-candidates/identity/`。保留实际 purpose/resource 匹配、当前会话范围、secret generation 与撤销语义；旧自有密码/session 管理改用 Better Auth。旧 Secret.resolve 返回复制 bytes，而 OS 回调仅清除原 buffer，这个接口改为整个资源使用都处于 `withSecret` 回调，不携带旧 ExecutionLineage/Evidence/fence 支架。

本轮核实了 Better Auth / `@better-auth/api-key` 1.7.11 的实际安装源码，副本在 `temp/spec-research/sdk-research/better-auth-1.7.11/`：API key permissions/限额属于 server-only 字段；启用后 metadata 可由拥有者填写和更新。因此 metadata 不能存放可直接采信的 Actor/grants/Consumer。服务端使用 verifyApiKey 的实际 key ID 和绑定委派记录建立身份。[官方 API key 参考](https://better-auth.com/docs/plugins/api-key/reference)、[admin access control](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/plugins/admin.mdx)

## 2. 身份与权限平面

| 范围 | 正式能力 | 生效依据 |
|---|---|---|
| Subject 行为与优先指令 | 查看/调整生活安排、行为偏好、当前追求、希望优先考虑的人或事情 | 明确的 Subject 行为管理授权；作为行为输入与理由保存 |
| 真实交往 chat | 发言、邀请、请求帮助、资料分享、反馈、主体是否接受 | 实际平台/本地交往身份与会话范围，经过主体感知和决定 |
| Worker / Author | 已采纳任务的工具执行，或世界作者的场景工作 | 宿主颁发的限定委派、Consumer、Task/World 范围与预算 |
| System | 模型/角色/Prompt、配置、Subject 供给、平台账号、数据和预算管理 | Better Auth 登录或受限 System 服务委派 |
| Machine | 服务启停、运行时安装、允许的目录/网络/桌面与维护工具 | 明确本机/远程机器授权；OS 身份及安装的机器 connector |
| Recovery | 正常管理不可用时，读取引导、修复认证、定位备份和执行有限恢复 | 本机管理员/安装所有者的独立恢复证明与显式操作 |

System 管理员不会因为 role 名为 admin 自动获得任意 OS shell、其他安装或所有秘密。Machine/Recovery 需要对应操作的实际授权。某个维护助手可同时具有特定 System/Machine 能力，但使用独立 Consumer、工作空间、凭据与生命周期。

同一真实人可具有软件管理身份和交往身份；入口明确区分。本地/平台消息作者只能由实际登录者或平台连接确定，不能凭正文里的“我是管理员”改变 Actor。显示名、群昵称、社会亲近程度和动机不参与授权。

行为优先指令影响注意、计划和表达选择，不能增加文件、渠道、角色或密钥权限。正式安装 policy 和资源限制仍执行。模型协议的 `system` role 负责 Prompt 编排，软件 System 权限由实际 authority 独立授予。普通聊天不直接修改这些管理设置。

## 3. 受信上下文与 scope

```ts
type AuthorityPlane = 'subject'|'system'|'machine'|'recovery';
type TargetScope =
  | {kind:'conversation';adapterId:string;accountId:string;
     conversationId:string;actions:string[]}
  | {kind:'resource';connectorId:string;resourceIds:string[];actions:string[]}
  | {kind:'workspace';workspaceRef:Ref;actions:string[]}
  | {kind:'object';refs:Ref[];actions:string[]};
interface DelegationScope {
  plane:AuthorityPlane;
  operations:string[];                 // 正式 operation catalog 中的明确操作
  subjectIds:SubjectId[];
  consumer:Consumer;
  purposes:string[];
  audiences:string[];
  targets:TargetScope[];
  inputRefs:Ref[];
  taskRef?:Ref;
  nativeBinding?:{runtimeId:string;sessionId:string;rootTaskId?:string};
  notBefore?:TimePoint; expiresAt:TimePoint; // 安全有效期必须 real
  mayDelegate:boolean;
}
interface ServiceDelegation {
  id:string;apiKeyId:string;parentAuthorityRef:string;
  issuerAuthorityRef:string;scope:DelegationScope;
  revision:number;state:'pending'|'active'|'revoked';
}
```

operations 由各 owner 注册到同一实际 catalog，包含所属平面、目标种类和所需权限。正常服务委派使用明确操作列表；新加一个管理操作不会因旧字符串前缀或隐式 `*` 自动授权给既有 worker。

HTTP/SDK 入口先验证 Better Auth session/API key，然后从实际账号或 apiKeyId 取得 authorityRef。Consumer、Subject、用途、听众和目标由当前委派与本次受信操作共同决定，形成 CallContext；公开业务 body 不包含可任意选择的 Actor、grants 或 credential。合法服务 caller 可以请求它获准范围内的 purpose/audience，宿主核验后填写 ctx；请求字段不是授予权限的依据。

消费者身份按绑定精确匹配 kind/host/id。Subject 逻辑身份可跨产品一致，但两个安装的服务身份与 Consumer 映射由显式连接授权登记；不把任意相同 id 的 worker 自动变成主体。专业任务还核对 root Task、原生 session/run 与当前允许工具，模型参数无法自选父任务预算或其他 worker 的私有范围。

authorityRef、parentAuthorityRef、issuerAuthorityRef 沿共同 Actor 的 authority locator，SecretRef 沿 credentials 的专用 opaque 合同；业务对象与 Clock/ClockSegment/TimeCapture 使用完整共同 Ref，opaque ID 字段使用 *Id。凭据 expiresAt/notBefore 使用 real 的纯安全时间读取；普通授权检查、query.prepare 和 query.run/expand 不执行业务时间捕获。观察、形成或实际效果所需 TimeCaptureReceipt 由实际业务 owner 保存，clock.capture 和资料读取分别检查各自 operation 权限。

Native origin 使用真实 SDK/runtime facts 校验，再作为 OriginIdentity 保存。runId、sessionId 和 callId 只是来源身份，知道它们不取得权限。恢复使用持久 authorityRef 重新取得当前委派，不使用一份早期 grants 快照继续派发。

### 3.1 委派的取得与缩小

授权人通过明确 `delegations.create/update/revoke` 操作创建服务凭据；普通 API key 创建/metadata 接口不获得产品委派权。Better Auth 继续拥有 token hash、enabled/expiry/ratelimit，产品 delegation 保存实际 Consumer 和业务 scope。主产品授权不在 metadata 或另一份可自行扩大的 permissions 副本中维护。

发行权限本身声明允许签发的 plane/Consumer 映射和最大 scope，使用 Better Auth 的正式角色操作权限与产品目标检查确定；不能把本次 ctx.consumer 当成任意发行资格。System 发行受限 Subject/Worker 服务是明确授权操作，Machine/Recovery 发行另需对应上界。

创建子委派时，逐项检查是当前 parent 发行上界与 scope 的子集：操作、Subject、Consumer 允许映射、purpose、audience、目标动作、输入来源和 native/task 绑定均不能扩张；有效期不晚于父授权。mayDelegate 仅在原授权明确允许时成立。子委派不能把 worker 范围提升成 Subject/System/Machine。

登记 token 与 delegation 无跨 owner 原子承诺：先形成受限 pending delegation，使用 Better Auth server API 创建 key 并绑定实际 ID，激活后才交付秘密；中途失败的 key 没有 active delegation，产品默认拒绝并可撤销。API key 只作 credential 校验，业务 scope 仍来自该绑定记录；客户端可写 metadata 不改变它。

服务密钥默认有效 24 小时、限速 600 次/分钟，运行任务子委派不超过父 Task 现实期限及父授权剩余时间。操作者可经正式设置选择其他期限；subject/world clock 变速不能延长凭据。已生成 token 的明文只在受控交付时给出，丢失交付通过显式轮换取得新 key，日志不补发原秘密。

## 4. 资料范围、用途与披露

共同 Policy 的 readers/purposes/audiences 使用真实身份与 scope registry 的稳定 ID。`*` 是明确通配，空集表示该维度没有许可；昵称、显示名称和模型生成 ID 不绑定授权。

读取须满足：当前 operation scope、Subject/对象归属、Consumer 私有边界、实际 reader 和 purpose。对外披露还必须把真实目标解析成非空 audience scope，并逐项满足所有来源的 audiences。内部审议可无对外 audience；这不授予之后的对外发送权。空 audiences 的私密来源无法向任何外部目标传播。

来源政策沿 input refs 递归求交，每项实际接触各自核验。相同 Blob hash、同一作者或同 SubjectId 不合并来源许可。冻结 QueryView、准备过的 Context、已缓存表示仍受当前撤回与来源限制约束；服务只返回本次 scope 可取得的完整区域及 omitted 原因。

worker/author 原件与草稿归其 Consumer，Subject 不因后台完成而知悉。`materials.publish` 使用受信工作者宿主授权选定已有结果，目标必须是同一 Subject 的允许范围；保留原依赖与传播限制，选定区域不夹带原始全量 Blob。Subject 真正消费后才产生对应 Encounter/Experience。System 管理员查看私有运行日志需明确数据审计权限，其读取不会替 Subject 写经历。

私有输入可以支撑后来的结论，但结论不能自行扩大来源披露。事实误解、故意隐瞒和社会姿态由认知/表达领域保存；它们不修改软件权限。

## 5. 当前授权与实际效果

`authorizeCurrent(ctx, operation, target)` 从 authorityRef 重新取得账号/委派和 parent 状态，检查过期、当前修订、Subject、Consumer、purpose、audience、目标、来源、角色/工具与预算。这个函数由产品组合到各实际资源/渠道 owner，通用库只提供已验证集合操作和凭据机制。

需重新检查的点包括：

1. 新模型/provider 调用前与未知操作的显式重试前。
2. 下载/staging 等异步准备结束后，真正平台发送、文件改写或其他外部效果之前。
3. 工具、浏览器、桌面与子代理启动时；子任务继承范围交集。
4. 冻结的后台成果被新 caller 读取、发布或对外使用时。

队列/工作流 ID 和保存的 Ref 不是权限。原生发送使用 SDK 的 onPlatformSendDispatch，在最后同步 handoff assert 核对同一宿主授权；产品领域在短事务中保存合法 dispatch 的事实，网络在事务外执行。取消/撤权后尚未派发的义务不执行；已经持久的 accepted 结果只补交后续记录，unknown 保留原操作，撤权不使其自动变成可重发。

Better Auth 的 credential 状态与产品 parent/delegation 变更共同参与当前检查。关键写点不依赖过期的 session cookie cache 或长期 authorization cache；库的快速缓存默认不用于需要即时撤销的 gate。current check 只读凭据当前 enabled/expiry 与授权版本，不重复消费一次 API 请求的 rate-limit 计数。

撤销 key、撤销委派、缩小 scope、禁用 Subject 或取消 Task 分别产生自己的正式变更。回调将现有待办标记需重查或取消，并让原 DBOS/native work 在下一 gate 停止；不创建全局权限轮询器。已发生的外部效果与历史证据按实际结果保留。

## 6. SecretRef 与平台后端

```ts
type SecretRef = string; // 产品注册的 opaque secret:<UUIDv7>
interface SecretMetadata {
  ref:SecretRef;revision:number;generation:number;
  state:'active'|'revoked'|'unavailable';
  purpose:string;resourceRef:Ref;allowedConsumers:Consumer[];
  backend:'os'|'environment'|'protected_file';
  configured:boolean;createdAt:TimePoint;replacedAt?:TimePoint;revokedAt?:TimePoint;
}
interface AuthorizedSecretUse {
  authorityRef:string;consumer:Consumer;purpose:string;resourceRef:Ref;
}
```

SecretRef 是产品秘密注册项，不是任意环境变量名或文件路径。locator、OS service/account、文件实际路径和 raw material 留在 credentials 实例。业务配置保存 SecretRef，权限仍由所属资源和当前 authority 检查；单独拥有 SecretRef 不取得明文。

实际使用为 `credentials.withSecret(ref, authorizedUse, callback)`，callback 直接调用正式 provider/channel/resource SDK。明文不进入 CallContext、Prompt、普通模型工具结果、DBOS 输入/step output、trace、portable package 或状态 API。需要 SDK string 时在 callback 范围构造；可控 byte buffer 在 finally 清理，SDK 内存生命周期由实际运行库管理。

| 平台/环境 | 后端 | 配置与行为 |
|---|---|---|
| Windows 桌面/本机服务 | Windows Credential Manager，经成熟 `@napi-rs/keyring` | 使用实际运行用户/服务账号的 OS store；权限与安装身份绑定 |
| macOS 桌面/服务 | Keychain，经同一成熟库 | 服务账号访问由安装明确配置；不可用返回 unavailable |
| Linux 有用户会话 | Secret Service/keyring，经同一成熟库 | 读取实际用户会话，缺会话时不假称 configured 可用 |
| Linux/Windows headless 或受管服务 | 显式 protected_file 或 environment binding | 安装时选择，支持成熟服务环境/凭据注入；不因 OS store 失败静默降级 |
| CLI 临时输入 | protected file / stdin / 环境引用 | 受控传入，不使用会被 shell 历史记录的明文命令参数 |

原 Hept 实际依赖 `@napi-rs/keyring` 2.0.0，并有 `AsyncEntry` 的 callback-scoped adapter；从已复制实现直接改编和核验 Node 24 平台产物，不再自制 OS 密钥仓库。protected file 只在安装 SecretRoot 内定位，阻止路径穿越及越界 symlink；Linux/macOS 使用目录 0700、文件 0600，Windows 使用实际服务 SID 的 ACL，不能把 chmod 当 Windows ACL。

environment binding 只解析预先由 System/Machine 配置的变量映射。资源调用不能让模型把任意 env name/absolute path 当 SecretRef 传来。环境型秘密的撤销先在产品 registry 关闭解析/新调用；对已向外部 provider 发放的 token，另走该 provider 的真实轮换/撤销操作。

### 6.1 引导秘密与启动顺序

数据库连接、认证签名和有限恢复所需的引导秘密必须在业务库打开前可取得。其 SecretRef、固定 purpose/resource 和私有 locator 由受保护安装配置持有，credentials 在真实本机 Bootstrap/Recovery authority 下解析，不先查询尚不可用的业务 registry。该安装配置是这些引导项的唯一登记来源；普通模型/渠道等资源秘密仍由产品 Secret registry 管理。

正常 API 的 secret status 可组合两类 metadata，但不把它们写成两份可变授权状态。修改引导项走明确的安装管理/本机操作。DB 不可用时，普通 resource SecretRef 不自动降级到任意文件或环境读取；Recovery 只取得事先声明的引导范围。

## 7. 秘密生命周期与故障

新建先把 material 放入选择的成熟后端，再提交 metadata；状态接口只返回 metadata。轮换保留 SecretRef，建立新 generation，CAS 切换当前 generation，成功后清除旧后端 generation；失败的新 generation 保持不可用或按实际 orphan cleanup 删除。不能把当前值原地改掉后再发现 metadata 回滚。

撤销先将 registry 状态改 revoked，阻止后续 resolve 与派发，再删除当前 backend material。删除后端失败返回 pending 范围，继续由同一实际操作收尾，不把状态报成完全擦除。env 后端不能由产品直接删父进程环境，需关闭 binding 并给出实际待轮换范围。

后端存储、数据库与外部 provider 没有跨系统原子提交；用正式 generation、原 operation 和状态说明事实，执行进度由 DBOS/成熟服务承担。秘密明文不作为可重放工作流输入；待完成的轮换引用受保护 generation 或 SecretRef，读取时再在 scope 内解析。

长期运行的 native/profile credential 通过受限 SecretRef 注入自己的隔离环境。主体模型不能读维护凭据；维护助手也不因能操作机器而自动获得其他产品原文和全部 Secret。原生 child 的工具/沙箱/网络范围由实际 native SDK 收窄，不能把 allowedTools 数字或文字只放 Prompt。

## 8. 正常管理与离线恢复

正常管理使用 Better Auth 会话、admin access control 与官方产品 API。两个产品使用各自 cookie prefix、签名秘密、认证库实例与数据库；联合 UI 明确连接两个会话，不共用同一个 cookie/key 伪装全局安装身份。服务 API key 默认不当浏览器 user session 使用。

密码、会话和 API key 由成熟库保存。产品不复制旧自有 authEpoch/session token/password verifier 表。现有 1.7.11 的 Date 字段在 auth adapter 边界归一为共同值，业务 ctx 不解析任意 metadata.actor。初始管理员认领只在空安装且经本机引导证明成立时进行；已有安装不开放重新 signup-admin。

离线 Recovery 由确定性 CLI 提供，不依赖模型、Hept 主体、QQ、Nous 或主 HTTP 服务。先验证本机安装所有者/管理员与受保护引导目录、locator 和实际数据库目标，取得限定的 Recovery capability；默认不会开放一个远程万能恢复 HTTP 入口。

| 恢复操作 | 实际范围 |
|---|---|
| `recovery.inspect` | 安装 locator、服务/数据库/credential 可用状态，脱敏输出 |
| `recovery.resetAdministrator` | 选定用户密码与其人类登录 session；保留 Subject、渠道和其他数据；服务 key 的撤销另明确选择 |
| `recovery.revokeCredential/rotateSigningSecret` | 指定 credential 或整产品 session 签名范围，展示实际受影响对象后执行 |
| `recovery.restoreBackup` | 已验证备份、目标实例和暂停后的实际产品恢复；恢复后按原 source/clock/effect closure 继续 |
| `recovery.repairLocator` | 经本机授权修改本安装路径/连接，不扩大业务权限 |

离线密码修复复用 Better Auth 的 password.hash 与 server adapter 的 findCredentialAccount/updatePassword/createAccount/deleteUserSessions 等实际路径；只由持有 OS Recovery capability 的本地组合调用，不暴露给聊天或普通 bearer API。使用其事务/adapter能力完成，不复制旧 Argon2 参数或手工伪造登录 token。修复后通过真实登录确认，输出只给 credential 的受控位置和状态。

Machine 维护助手可协助调用这些确定性操作，但其权限来自单独机器授权。停止服务、修复 PG 或更换密钥不由 Subject 的愿望、亲密关系和普通对话驱动。

## 9. SQL、操作与审计

Better Auth 的 user/session/account/apiKey 表及迁移由库持有。产品附加范围采用最小正式记录：

```sql
service_delegations(id uuid PRIMARY KEY, api_key_id text UNIQUE,
  parent_authority_ref text,issuer_authority_ref text,state text,revision bigint,
  scope jsonb,created_at timestamptz(6),revoked_at timestamptz(6));
subject_bindings(id uuid PRIMARY KEY,subject_id uuid,connection_ref jsonb,
  local_consumer jsonb,remote_consumer jsonb,revision bigint,state text);
secret_records(secret_id uuid PRIMARY KEY,revision bigint,generation bigint,
  state text,purpose text,resource_ref jsonb,allowed_consumers jsonb,
  backend text,private_locator jsonb,created_at timestamptz(6),revoked_at timestamptz(6));
```

操作与审计复用正式 owner history、trace 和 DBOS operation，不新建通用权限工作流引擎。审计保存实际 actor/authority、Consumer、Subject、purpose/audience/target、采用 scope revision、结果和 operation/trace 引用，明文秘密及未授权正文不进入日志。

| 正式能力 | 规则 |
|---|---|
| `auth.login/logout/session/list/revoke` | 使用 Better Auth 正式会话与实际登录身份 |
| `delegations.create/read/update/revoke` | 授权入口管理范围，CAS 与父授权交集，普通 metadata 不改权限 |
| `subjects.bind/permissions.read/update` | Subject、连接与允许目标分离；社会身份不自动映射软件 admin |
| `secrets.create/status/rotate/revoke` | 明文只在受控写入/使用 callback，status 不返回 material/locator |
| `native.authority.check` | 实际 runtime/session/Task 绑定与当前来源、工具、目标重验 |
| `recovery.*` | 仅本机限定 Recovery capability，确定性管理与真实结果 |

导出业务资料保留逻辑 binding/secret 需求，operator connection 和明文 Secret 留在安装设置。整安装受控备份若包含秘密，使用成熟加密备份并记录其保留范围；清除 registry 关闭后续解析，独立备份删除和 provider token 撤销由各实际 owner 完成并返回完成与 pending。

## 10. 迁入和必要检查

复制源：旧 Hept `secret/contracts.ts/service.ts`、`os-credential/src/index.ts`、QQ `policy.ts`、management contracts 和 bootstrap authority。迁入共享 credentials 的是成熟后端使用和 generation/资源匹配；迁入各产品的是业务 scope/委派。旧自有密码/session、硬编码 gateway-only secret consumer、raw bytes 返回接口与 Host fence 退出当前消费者。
