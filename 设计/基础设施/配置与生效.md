# 配置与生效

## 采用与所有权

`@nous-wave/platform/settings` 复用 Zod、`@fastify/deepmerge`、`fast-json-patch`、PostgreSQL/Kysely 和 LISTEN/NOTIFY，提供定义目录、稀疏覆盖、求值、修订及来源视图。Nous 和 Hept 各创建独立实例、迁移各自数据库。领域注册自己的定义和变更处理；库不认识 World、Memory 或 Reactor。

从原 Nous `apps/nous-core/src/configuration/catalog.ts`、`crates/configuration/src/snapshot.rs` 迁入定义元数据、不可变快照和查询局部覆盖语义；保留原 Hept Definition/Revision/Activation 中实际需要的保存/生效区别。当前重建 `management/settings.ts` 可迁入 SQL/CAS、通知和数组替换部分，其输入默认值污染、运行修订推定和不完整字段需要替换。具体事实见[基础设施研究](../../研究/基础设施与现有结构.md)。

## 模块定义与共同类型

模块使用无默认值的约束 schema 和独立产品默认值。Zod 校验最终有效对象，JSON Schema 加上定义元数据供管理界面使用。

```ts
interface SettingsModule<T> {
  id:string;                    // nous.retrieval / hept.attention / platform.network
  definitionRevision:string;    // 随该定义的代码/资源版本变化
  owner:string;
  schema:ZodType<T>;             // 完整有效值约束
  defaults:Readonly<T>;
  fields:Record<string,FieldMetadata>; // JSON Pointer -> 字段语义
  validate?(value:T,context:ValidationContext):Promise<void>;
}
interface FieldMetadata {
  labelKey:string;
  descriptionKey:string;
  scopes:('installation'|'subject'|'role')[];
  visibility:'standard'|'advanced'|'developer';
  effect:'hot'|'next_call'|'restart';
  unit?:string;
  readonly?:boolean;
  restriction?:'upper_bound'|'set_intersection';
  consumerIds:string[];
}
type ConfigScope =
  | {kind:'installation';installationId:string}
  | {kind:'subject';subjectId:string}
  | {kind:'role';subjectId:string;roleId:string};
interface RevisionRef { namespace:string; scope:ConfigScope; revision:number }
interface ConfigSnapshot<T> {
  values:Readonly<T>;
  sources:Record<string,{source:'default'|'override';revision?:RevisionRef}>;
  revisions:RevisionRef[];
  definitionRevision:string;
}
```

模块定义静态组合进产品，不增动态配置插件总管。字段 metadata 可由各模块 `.meta()` 导出，但不可从 Zod 私有 AST 手工生成另一套默认值或运行模型。秘密字段只接受 SecretRef。

## 四层求值与稀疏修改

顺序为产品默认、安装、Subject、该 Subject 的 Role。持久化后三层的稀疏覆盖；缺失表示继承，显式 null 仅在 schema 允许时表示空值。对象递归合并，数组整项替换。

```ts
const merge = deepmerge({mergeArray:({clone})=>(_old,next)=>clone(next)});
const sparse = [installation, subject, role].reduce(merge, {});
const effective = module.schema.parse(merge(module.defaults, sparse));
```

默认值只在所有覆盖合并后一次应用。当前 Zod 4 带默认字段的 `.partial()` 会为缺失值补默认，不能将其作为稀疏输入解析器。采用标准 JSON Patch 对本层稀疏 JSON 操作，最终对象统一校验：

```ts
interface SettingsChange {
  namespace:string;
  scope:ConfigScope;
  expectedRevision:number;  // 初次为0
  patch:Operation[];        // RFC 6902，库校验路径与操作
  reason?:string;
}
interface SettingsReset {
  namespace:string;
  scope:ConfigScope;
  expectedRevision:number;
  paths?:string[];          // RFC 6901；省略清除本层全部覆盖
}
```

稳定提交身份由SDK选项/Idempotency-Key进入调用上下文，见[共同提交合同](共同值与调用上下文.md#提交身份与幂等)。SettingsChange/Reset的body不重复该传输字段。

JSON Patch 使用 `applyPatch` 的验证和 prototype 修改保护；只允许本定义声明的路径和作用范围。删除覆盖不将 defaults 写进当前层。未知键、无效引用、越界值和跨字段约束由最终 schema 与 owner.validate 拒绝。同一层的完整数组始终来自一个修订。

## 权限、预算和原生设置

普通值按后层覆盖。被标记为上限的预算字段，按各授权层的显式上限收紧；下层扩大值不会扩大上层许可。权限允许集合按上层限制与当前委派共同求交。普通数组仍整体替换，不能把所有数组都当授权集合。

设置的偏好、授权的硬限制、实际领域状态分别表达。例如日历参与策略是设置；某项活动已经采用、当前 WorldClock 的分段速率是领域事实。改当前时钟调用 clock.configure 等操作，不同时写一份可变 settings.clock.rate 镜像。

OpenClaw 的原生模型、Skills、渠道账号、浏览器和插件设置继续由其正式 API 修改。管理页可以聚合读取原生配置与产品定义，字段声明真实 owner 和 revision；产品保存 native resource/binding 引用，不重复维护原生配置正文。AstrBot 可选插件同理。

## 数据库

```sql
create table settings_definitions (
  namespace text not null, definition_revision text not null,
  json_schema jsonb not null, defaults jsonb not null, metadata jsonb not null,
  recorded_at timestamptz(6) not null default clock_timestamp(),
  primary key(namespace,definition_revision)
);
create table settings_changes (
  operation_id text primary key, namespace text not null,
  scope_kind text not null, scope_id text not null, actor_ref text not null,
  request_digest text not null, result jsonb not null,
  recorded_at timestamptz(6) not null default clock_timestamp()
);
create table settings_revisions (
  namespace text not null,
  scope_kind text not null,
  scope_id text not null,
  revision bigint not null,
  definition_revision text not null,
  sparse jsonb not null,
  patch jsonb not null,
  actor jsonb not null,
  reason text,
  recorded_at timestamptz(6) not null default clock_timestamp(),
  primary key(namespace,scope_kind,scope_id,revision)
);
create table settings_heads (
  namespace text not null,
  scope_kind text not null,
  scope_id text not null,
  revision bigint not null,
  primary key(namespace,scope_kind,scope_id),
  foreign key(namespace,scope_kind,scope_id,revision)
    references settings_revisions(namespace,scope_kind,scope_id,revision)
    deferrable initially deferred
);
```

head 只指向不可变稀疏修订，当前有效值是求值视图。definitions保存各已注册版本的不可变JSON Schema/defaults/元数据，历史查看不依赖已经改掉的代码默认值；恢复仍用当前可执行schema校验。changes是设置owner的最小成功回执，含no-op/reset/restore，不保存任务进度、重试或租约。安装 scope_id 是 installationId；Subject 是 SubjectId；Role 使用无碰撞的 `(subjectId,roleId)` 编码，不靠未经转义的随意字符串拼接。

更新由短 owner 事务完成：当前授权；按operationId提交范围取得PG事务锁并查changes；相同request_digest直接取得原result，不同内容冲突；新提交再锁head并比较expectedRevision；读取相关覆盖和引用；应用patch、求值/校验；如有改变插入revision并CAS改head；保存包含原结果/实际revision vector的changes回执；同事务 `pg_notify('settings_changed', {namespace,scope,revision})`。已不存在的reset不改head，但仍保存原changed=false回执。规范输入摘要采用稳定JSON库，包含scope/namespace/操作/patch或restore目标与受信调用范围，不包含后生成的当前时间/默认值。重放同submissionId先返回原成功回执，当前授权仍检查；成功后的运行生效状态通过实际消费者单独查询。

首次写入使用唯一键冲突与行锁保证 expectedRevision=0 的并发语义。禁止先读不到就无条件覆盖另一调用已经创建的第一修订。

## 快照与实际生效

单次调用取得一致的 revision vector。一次 SQL 读取相关 heads/versions，或在只读 repeatable-read 事务读取全部所需 namespace，避免混合两次修改中的半份设置。冻结快照不被后续通知原地修改。

- hot：owner 在提交后应用新版本，成功后报告实际 applied vector；失败显示已保存修订与生效错误。
- next_call：下一次完整模型/查询/任务规划读取新快照；已经运行的调用仍使用原快照。
- restart：保存 desired 版本，运行实例继续报告本次 boot 使用的版本。重启成功后才报告 applied。

`runningRevision` 不能仅因 SQL 保存成功就等于新修订。运行状态带 processBootId/consumerId 与已采用 vector；这份状态来自真实消费者，持久配置仍只有 revision/head。

单进程直接通知已注册消费者。多进程使用 pg 的 LISTEN/NOTIFY：通知携带身份和修订，不带配置正文。启动和重连重新读取 head；调用边界检查所需版本，失联期间缓存不作为授权或预算事实。通用缓存使用成熟 LRU，namespace/scope/revision/definitionRevision 为键。

配置保存不在一个数据库事务内调用模型或等待网络重载。真正长的资源重建由 owner 返回 OperationRef；进度来自 DBOS。通知不发展成另一套持久事件总线。

## 公共操作与管理

```ts
settings.describe(ctx,{namespace?,scope?,definitionRevision?}) -> ModuleDescription[]
settings.read(ctx,{namespaces,scope,roleId?}) -> EffectiveSettingsView
settings.update(ctx,SettingsChange) -> SettingsChangeResult
settings.reset(ctx,SettingsReset) -> SettingsChangeResult
settings.history(ctx,{namespace,scope,cursor?,limit?}) -> CursorPage<SettingsRevision>
settings.restore(ctx,{namespace,scope,revision,expectedRevision}) -> SettingsChangeResult
```

恢复历史以新修订采用旧 sparse，不改历史行。已被代码删除的字段由正常定义迁移报告或转换，不能绕过当前 schema。恢复结果同样运行当前引用和授权校验。

HTTP 对应 `/v1/settings/schema`、`GET/PATCH /v1/settings`、`POST /v1/settings/reset`、`GET /v1/settings/history`、`POST /v1/settings/restore`。SDK 保留 namespace/scope、原错误和 revision；CLI 提供 get/set/reset/history/restore，set 可读标准 JSON Patch 文件或专用字段交互；Web 从 Describe 展示来源和恢复继承，关键模型/Prompt/时钟操作用专用页面。

联合管理分别读取两产品的实际设置与 native 设置，显示 owner，修改发送给真实 owner，不在组合界面再存可变副本。用户界面语言、Prompt语言和主体自然语言各自配置。

## 失败与生命周期

- schema/path/跨字段错误：400，保存前拒绝，给具体字段与 messageKey。
- expectedRevision 变化：409，返回当前修订，不覆盖他人修改。
- 服务/模型不可用：普通配置保存可继续；需要外部验证的显式 probe 报对应依赖状态。
- hot 应用失败：已保存修订仍可查；运行值保留原版本，显示实际失败消费者与重试入口。
- 重启：加载定义，迁移覆盖，读取最新 head，再启动相应组件；重连通知后重新取 head。
- Subject Bundle：按授权导出所选 Subject/Role 覆盖和必要资源引用；安装级模型地址、秘密与机器路径由导入者重新绑定。
- 删除 Subject：删除其 scope heads/revisions 与派生缓存；安装定义和其他 Subject 不受影响。

验证用一条配置—Prompt—真实调用路径，加无默认稀疏合并、数组替换、上层限制、CAS与restart生效差别的必要规则。通用合并和 JSON Patch 库内部规则沿用上游测试。
