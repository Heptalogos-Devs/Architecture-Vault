# 观测错误与诊断

## 采用与职责

采用 Pino 结构化日志、OpenTelemetry JS、官方 DBOS 查询及所属领域的正式事实。`@nous-wave/platform/telemetry` 组合成熟库；各产品独立实例、目录与配置。共同 Problem 和 `CallContext.trace` 直接使用[共同值合同](共同值与调用上下文.md)，事务与 checkpoint 边界见[存储事务与缓存](存储事务与缓存.md)。

| 资料 | 回答的问题 | 实际 owner |
|---|---|---|
| Pino 日志 | 哪个组件何时发生何种安全分类的行为/故障 | 产品 telemetry |
| OTel span/metric | 调用关联、时延、资源压力与依赖 | 标准 instrumentation / 实际执行边界 |
| DBOS 状态/步骤 | 哪项持久工作正在等候、恢复或结束 | 官方 DBOS |
| 调用/发送/效果回执 | 是否真实派发、返回、计费、效果未知 | model / communication / tool / operations owner |
| 来源、实际消费与认知谱系 | 用过哪些固定对象、区域、版本及观察点 | Source、Encounter、认知领域、query |
| 受限诊断 Artifact | 经授权保留的必要原始诊断与输出 | 数据/Artifact owner |

不把上述资料复制到一个通用事件/证据数据库。普通短操作可直接记录日志和 owner 结果；无需为每次读建立 DBOS workflow 或操作状态行。

两产品的持久操作读取使用同一 `contracts/runtime` 的 `OperationViewSchema` 与 `OperationTraceSchema`。公共状态为 queued/running/waiting/completed/failed/cancelled；保留实际 `nativeStatus`、operationId、真实引擎毫秒时刻、选定的 Subject/trace/父操作/queue/version/recovery 与安全 Problem。Trace 为 `{operation,steps}`，步骤只含 functionID、name、状态、childWorkflowID、起止毫秒和安全 Problem。输入、输出和任意 attributes 不进入通用操作响应，实际内容从所属 owner 读取。

`platform/storage` 的 `describeDurableWorkflow`、`describeDurableSteps` 在正式 SDK 事实上作同一投影。产品入口先检查当前操作权限和 Subject 范围。明确恢复经 `resumeDurableWorkflow` 使用 DBOS 5.3 原生 API：ERROR 从首个失败 functionID rewind，其他状态按 SDK resume；保持原 workflowID 和已完成步骤。领域回执与模型 ledger 仍决定已有外部效果的采用，未知调用继续核实原操作。需要恢复失败子工作流时直接选择该真实子操作，不创建新的 Task 或付费调用来替换它。

## 关联与本地可用

入口建立受信 `ctx.trace`，字段为 traceId、operationId 及可选 traceparent、invocationId、taskId、effectId；Consumer/Subject 从可信调用上下文取得。Pino 使用 `.child()` 绑定这些允许字段及 product/installation/component。外部 traceparent 用 OTel `propagation.extract/inject` 继续关联，身份和权限仍由正式入口验证。[OTel 传播](https://opentelemetry.io/docs/languages/js/propagation/)。

普通记录使用固定 event 名、等级、结果分类、耗时、资源标识和安全 Problem；正文、Prompt、模型响应、私聊、原始 URL query、工具 args、凭据不作为默认字段。high-cardinality trace/object ID 进入日志/span，metric labels 只使用有限 component/operation/model family/result/category 等集合。

本地默认保留 stdout JSON 和产品 DataRoot 下独立的轮转日志。用 `pino.transport` 配置 Pino stdout/file target，文件采用 `pino-roll` 的 size/frequency/limit 机械；目录由本安装独占，历史 count 明确不含当前活动文件。跨重启清理采用该独占目录的保留配置，不扫描其他安装。默认 info；debug 有明确期限、范围与管理员操作。[Pino API](https://github.com/pinojs/pino/blob/main/docs/api.md)、[transport](https://github.com/pinojs/pino/blob/main/docs/transports.md)、[pino-roll](https://github.com/mcollina/pino-roll)。

OTLP 是可选输出。未配置 OTLP 时，CLI/Web 仍能分页查看本地日志、安全 operation 元数据、官方工作步骤、owner 回执和来源查询。OTel NodeSDK 只装一次；用 `startActiveSpan`、标准 Resource 和配置的 BatchSpanProcessor/Exporter，不同时启动两套全局 TracerProvider。DBOS 配置外部 provider 时采用 `tracingEnabled`，不再开其内置 OTLP provider。[OTel instrumentation](https://opentelemetry.io/docs/languages/js/instrumentation/)。

### 共享实例的实际组合

```ts
const telemetry = createTelemetry({
  product:'nous', installationId, paths, mode:'service',
  bootstrapLevel:bootstrap.logging.level, processBootId,
  events:['http.completed','query.completed'],
  headers:ref => host.readOtlpHeaders(ref),
});
const settings = createSettings({installationId,db,modules:[telemetryDefinition],authorize});
await settings.registerDefinitions();
await telemetry.bindSettings(settings);
DBOS.setConfig({name:'nous',systemDatabaseUrl,logger:telemetry.dbosLogger,
  enableOTLP:false,tracingEnabled:true});
```

`logger`是稳定的原生Pino实例；`component(name)`返回组件child，`forContext(ctx,name)`只绑定允许的身份与trace字段。产品固定事件名在`events`声明；未知字符串记录固定分类，未知对象只投影允许字段。message、Error.stack/cause、Prompt、正文与任意嵌套对象不进入日志。原生Pino hook和bindings formatter覆盖普通logger及child入口，保持其原生等级、child、serializer和传输机械。未知event值不作为正文透传。

`span(ctx,name,async traced=>...)`使用官方extract/inject及startActiveSpan，把真实span的traceId/traceparent写入传给回调的新CallContext；Actor/Consumer和操作身份保持原值。后续HTTP/模型/DBOS调用使用该traced上下文。错误只设ERROR状态和安全code/category，不调用`recordException(raw)`。

共享库导出`telemetryDefinition`，其`platform.telemetry`定义使用独立schema/defaults：

| 字段 | 默认 | 生效与实际消费者 |
|---|---|---|
| level / components | info / 空组件覆盖 | hot；telemetry.logger直接修改Pino.level及已注册组件child |
| console.enabled | true | restart；服务写stdout，CLI写stderr，CLI stdout只承载命令结果 |
| file | enabled=true，10MiB，daily，historyCount=7 | restart；telemetry.logger，独占Paths.log/telemetry/events*.log |
| otlp.enabled / protocol / endpoint / headersRef | false / http/protobuf / null / null | restart；telemetry.otel；endpoint是Collector基础地址，HTTP按信号追加v1/traces或v1/metrics |
| otlp.timeoutMs / queueSize / batchSize / delayMs | 10000 / 2048 / 512 / 5000 | restart；原生BatchSpanProcessor的有界队列 |
| otlp.sampleRatio / metricIntervalMs | 1 / 60000 | restart；原生ParentBased+TraceIdRatioBased与PeriodicExportingMetricReader |

bind前只有Bootstrap日志等级；bind时用注册消费者`snapshot()`读取正式配置，不借用管理账号。bind完成报告实际采用vector。之后订阅设置通知只热改level/components；file/console/OTLP保存后仍显示pending，重启后才报告新值。文件不可写时去掉失效sink并报告`/file`不可用，已失效的旧applied记录被清除。

固定复用Pino10.4.0、pino-roll4.0.0、OTel API1.9.1、NodeSDK/exporters0.208.0、resources/trace-base/metrics/core2.2.0和grpc-js1.14.6。pino-roll的数字size单位是MB，调用处将正式sizeBytes转换为显式k单位；limit.count是历史文件数，不含活动文件。removeOtherLogFiles只用于该安装独占的telemetry目录，跨boot历史在下一次原生轮转清理。

HTTP使用官方异步headers factory逐批取得凭据；gRPC使用原生MetadataGenerator逐RPC取得凭据，带身份时要求TLS。不把明文header快照存进配置或持久实例。NodeSDK关闭检测器和自动instrumentation，Resource只含静态产品/安装/boot/版本；AI SDK与实际owner按各自语义添加安全spans。

OTLP关闭时仍由同一NodeSDK的官方NoopSpanProcessor产生本地trace身份，原生MetricReader使用DROP聚合，不启动导出或维护另一份trace缓存。OTLP开启时直接换用官方Batch/Periodic与HTTP protobuf、HTTP JSON或gRPC exporter。exporter薄投影去掉DBOS已证实的status.message、异常事件原文和错误属性，保留工作流/操作身份、trace父子关系和重试间隔；metric仅保留component/operation/modelFamily/result/category标签。

NodeSDK0.208会从OTEL_LOG_LEVEL自行安装Console logger；OTLP exporter会把环境headers合并到显式factory。正式运行若存在这类冲突环境（OTEL_LOG_LEVEL、OTEL_EXPORTER_OTLP_HEADERS、OTEL_EXPORTER_OTLP_TRACES_HEADERS、OTEL_EXPORTER_OTLP_METRICS_HEADERS或启用的OTEL_SDK_DISABLED），返回`telemetry.environment_conflict`并指出变量名，值不进入Problem。等级和身份分别使用Settings与SecretRef。

`flush()`等待Pino transport确认、标准console写完成及OTel forceFlush；`close()`关闭transport和NodeSDK，按期限返回实际关闭失败。DBOS不关闭调用者logger，组合根先shutdown DBOS，再close telemetry。只清理本实例实际拥有的OTel全局注册，重复close使用同一结果。

## Problem 与安全错误边界

Problem 的 `category/code/messageKey` 是机器可依赖分类；message 是安全可读回退文字，args/details 由 owner 白名单选择。owner code 表达具体原因，如 `sources.policy_denied`、`query.asset_incompatible`、`models.effect_unknown`；HTTP、CLI、MCP 和 SDK 只做各自传输。可重试条件使用正式 `retry`，不是看到 500 就重发。

本地 `ProblemError` 可以提供 Error 栈供开发调试；跨 DBOS/JSON 后按 Zod 验证的 Problem 识别，不依赖恢复对象的 class 身份。实现注册官方 `DBOS.registerSerialization` recipe：选择本地 ProblemError、序列化其已验证 problem、反序列化再构造。无需自定义 DBOS serializer。

本轮实测 5.3：workflow/step 的 serialize-error 会保存枚举属性并递归 cause/AggregateError.errors；Kysely datasource 的默认 SuperJSON Error 会丢失自定义 problem。官方 recipe 在两条路径保存了同一 Problem。错误必须在进入该边界前安全化，不能等到最终 HTTP handler 才处理。

| 原始入口 | 边界处理 | 保留的有效语义 |
|---|---|---|
| AI SDK Provider doX / stream error part | 官方 durableCalls 内部的 Provider wrapper 生成安全 SDK 异常；然后 SDK 继续处理 | status、requestId、官方 retry 分类、操作身份 |
| 工具 execute | 实际工具 owner 出口形成安全 Problem/结果，正文保存受限材料 | 派发与实际效果分类、调用引用 |
| PG/Kysely | owner/data adapter 在 checkpoint 前删除 query/参数/detail；保留 SQLSTATE 和允许约束名 | 40001 官方重试、CAS/唯一冲突分类 |
| 文件/网络/解析库 | 固定 code、安全资源身份和必要状态；去掉秘密路径/响应原文 | bytes/timeout/取消/完整性等实际原因 |
| 未知 Error/AggregateError | 默认 `failed` 安全文本、关联 ID；不序列化 raw message/cause | 可定位组件和受限 Artifact 引用 |

PG 的 retry code 不能在安全化时丢掉；datasource 5.3 实际只认 `40001`。序列化/唯一冲突和死锁各按真实语义处理。固定消息与代码选择应在负责的 adapter/owner 处完成，不再建一个猜测所有业务错误的中央平台。

### SDK 原文的真实入口

`APICallError` 可持有 `requestBodyValues / responseBody / responseHeaders / data / cause`；message 自由文本也可能含完整输入。Pino 字段 redact 只能匹配结构路径，无法删掉已经拼进 message/stack 的原文。OTel `recordException(raw)` 和 DBOS 默认 Error 序列化同样会传播它。[Pino redact](https://github.com/pinojs/pino/blob/main/docs/redaction.md)。

模型 owner 在官方 durableCalls **内层**接住原错误，构造安全的官方 `APICallError`，保留 `statusCode/isRetryable` 及允许的 requestId/header，清空 requestBodyValues、responseBody、raw cause/data，并使用固定安全 message；这样 SDK 的官方错误标记和重试分类仍在。流式 doStream 返回后的 error part 也通过同一标准 TransformStream 处理，保持背压/取消。完整规则和真实 doX 位置见[模型供应与调用](模型供应与调用.md)。

流的reader.read拒绝及cancel错误不会经过transform的error part分支；使用标准ReadableStream/getReader薄guard同时安全化这些异常，再交durable wrapper，保留背压、结束与取消。错误安全边界不另存流进度或复制原流。doX内的ModelInvocation事务是普通Kysely短事务，后续领域采用才使用datasource，避免在官方SDK step内再开datasource事务。

官方vercel-ai0.5.4的durable wrapper默认允许重试；本产品显式`retriesAllowed:false`、`include:{requestBody:false,responseBody:false}`，SDK `maxRetries:0`。仍保留官方错误分类，实际ModelInvocation gate阻止进程恢复时重派unknown效果。官方包已恢复replay后的AI SDK错误标记，不额外实现一套identity修补。需要的实际请求/结果由正式owner按政策保存为材料，避免durable wrapper额外复制正文。

AI SDK telemetry 显式设置 `recordInputs:false, recordOutputs:false`；默认原文记录不能依靠 trace UI 隐藏。SDK 聚合 RetryError 的各层、Provider/原生宿主 logger 和工具异常都纳入这条边界；外层再将安全分类映射为公共 Problem。实际输出先保存后业务解析失败时，费用、原结果材料和失败 Problem 分别保留。

### DBOS 自身日志

使用官方 `DLogger` → Pino 的薄 adapter，并设置 `DBOSConfig.logger`。DBOS 5.3 会先把日志转字符串；error 还会在 metadata.stack/error 传原对象。adapter 对应用 Problem 记录白名单，对未知内部事件记录安全 component/level/context/classification，丢弃未知自由文本及 stack/error。SDK 已知的无原文状态消息可按显式 allowlist 通过。该适配不解析 raw message 来恢复业务分类。

5.3启动的`System Database URL`消息、step重试事件的error属性和span.status.message已在实际源码确认。custom logger保留workflow ID及operation name，原Error只读取正式Problem的安全分类，message/details/args均不透传。静态`DBOS.migrateSystemDatabase`会直接创建默认GlobalLogger并忽略DBOSConfig.logger；组合根使用正常launch自动迁移及Kysely迁移，不经该快捷入口。

这覆盖官方连接池错误也可能拼 raw error stack 的入口。上游 Provider/owner 的安全化仍必须先做，因为 logger adapter 不控制 checkpoint。DBOS 的 logLevel 不会预先过滤 custom logger，由 adapter 按配置路由；DBOS 不关闭该 logger，产品负责 flush/close。adapter 不回调 DBOS.logger。[官方 logging 合同](https://docs.dbos.dev/typescript/tutorials/logging)。

## 受限原始诊断

确有排错需要时，先去除 API key、Authorization、cookies、签名 URL、连接凭据等秘密，再把必要 raw 诊断保存为 Artifact。Artifact 持有当前 Policy、Consumer scope、调用/源固定 Ref、形成/记录时间、类型、bytes 和保留截止；普通日志只含其 id 与保存状态。其原文读取使用数据管理/明确诊断授权，不能沿普通 trace 权限自动取得。

捕获失败仍返回原安全分类，另带 `diagnostic_unavailable` 元数据；不把原错误写回 stdout 补救。raw 捕获默认关闭，按短期调查范围开启。已保存模型输出、原件与 raw 诊断可能有不同正式保留义务，界面说明具体类别和依赖，不统一删掉或永远保留。

DBOS 输入、步骤输出和错误也是潜在私密保存位置。正式工作输入只传必要 refs、冻结配置和小量元数据，字节/大正文保留在 owner 材料。SDK 必须 checkpoint 的敏感结果通过同一数据权限、备份和期限管理；日志安全不会自动改变 checkpoint 内容。

## 官方工作查询与控制

正式`operations.inspect`读取实际owner回执及DBOS进度，目录、等待与控制使用统一的`operations.list/inspect/events/cancel/reconcile`；查持久工作时先用 `DBOS.listWorkflows({workflowIDs,loadInput:false,loadOutput:false,...})` 取得元数据，再依据受信 attributes 中的产品、Subject/Consumer 和正式授权检查。未知/无权对象不加载结果。只有显式授权的结果查看才读取对应 owner 材料/结果。

工作步骤使用 `DBOS.listWorkflowSteps(id,{limit,offset})`。5.3 实现内部会载入 output，因此必须先授权整项工作、限制分页，并立即投影允许的 functionID/name、时间、子工作 ID 和安全分类；不把原 StepInfo.output/error 直接返回。普通“查看 trace”不包含完整 request/response。[DBOS 官方 reference](https://docs.dbos.dev/typescript/reference/methods)。

状态显示直接映射官方 PENDING/SUCCESS/ERROR/CANCELLED/ENQUEUED/DELAYED 等值及实际 owner 状态。取消、resume/fork、删除使用官方操作；取消意图不能抹去已发生外部效果，unknown 的核实仍归效果 owner。管理 UI 先给实际阻塞原因、等待对象、成本和允许动作，不建立影子 workflow 状态机。

## 来源、用量与资源诊断

来源查询读取正式固定 Ref、revision 和 Selector，再经各 owner 批量读取。包括 node.pointer、media.startUs、实际 input portions、独立根、producer、知识有效时间及实际观察点；当前 scope/policy 和跨产品撤权每次核验。traceId 负责调用关联，来源 refs 负责内容与认识谱系，不能相互替代。

采用原有有界展开：节点/正文 bytes/层数预算、批量 owner 读取、明确 continuation/omitted 原因，精确 root 保持完整语义单元。查询算法诊断保留实际 assets/lane/过滤和数值中间量；未测量的值为空。完整内容通过 owner 的 `query.expand`/source trace 取得，不展开进普通日志。

模型诊断按 physical call 查询实际 Provider/Model/Role/Prompt 修订、输入来源、SDK step/attempt、派发/完成、原 usage 字段及结算。language 的 input cache/noCache/cacheRead/cacheWrite、output text/reasoning 与 embed tokens 等按模型族保留；provider 未给时标 unknown，不填 0。逻辑 total、SDK totalUsage 与逐实际调用 ledger 是派生聚合，不能重复计费。价格版本、货币、预留、实际、估算与人工核实分别标识。

跨产品根Task显示Hept的BudgetAllocationReceipt及稳定childOperationId、分配币种/额度、已结算/仍占用额度、Nous实际ModelInvocation引用与账目owner。Hept预留不是第二笔Provider实际费用；总览按原调用Ref去重并分别汇总各币种。unknown同时显示真实调用待核实与保留子额度，重试结算沿原回执，不新建一份分配。对端不可用时报告核验状态，后续派发按预算合同停止。

导入/fork显示原调用与预算分配的来源安装和历史性质；历史分配的issuer/target不因本地RefMap变为新授权。成本总览按实际执行身份去重，分支继承记录与本分支新支出分别展示，根预算只消费当前合法分配。清除剩余unknown/预留时显示最小无正文pending，不能把已删日志当作已结算。

资源压力直接采集 pg Pool total/idle/waiting、查询/锁耗时、DBOS 官方队列与运行量、Lance/Rust 资产 bytes/句柄、Blob 临时空间、进程 RSS/heap/event-loop delay、模型网络耗时/取消。metric 有界采样；压力量和阈值在管理中显示对应资源。预算不足、能力不可用、资源压力和效果未知使用各自 Problem 分类。

## 设置、保留、导出与停止

`platform.telemetry` 定义日志等级/组件覆盖、stdout/file、轮转 bytes/frequency/count、默认诊断保留、raw 开关/范围、OTLP 地址/协议/超时/队列、采样。设置使用独立无默认基础 schema、defaults 与稀疏 patch；秘密 endpoint header 从 credentials 取得。业务内容策略由相关 owner 定义，不能让 logLevel 授予原文查看权限。

诊断查询支持时间、operation/trace/invocation/task/effect、component、category、有限条数/bytes 和真实续页；源内容返回受限 ref。导出经相同权限选择安全日志、设置修订、版本、资源状态、官方工作元数据及明确选择的 Artifact；生成 manifest/digest/保留范围，默认排除秘密和私聊原文。跨产品诊断通过各自正式 Client 合并，管理端不直连邻产品表。

保留/删除覆盖活动轮转文件、raw Artifact、官方工作历史及备份。使用 DBOS 官方完成工作删除/清理 API，不改其内部表；尚有领域恢复依赖时先由 owner 处理。删除结果报告实际保留依赖与尚未删路径。业务回执按领域期限，不因为日志轮转丢失。

OTLP 断连时有界队列丢弃/重试只影响遥测，记录安全计数和当前 exporter 状态；不阻塞正式业务事务，也不把内存当无限日志仓。磁盘满时显示本地日志故障和 resource_pressure，受限 Artifact 写入失败不能回退为 raw console。停止依次停新接纳、保存实际效果、关闭 DBOS、Pino flush/transport.end、NodeSDK.shutdown，均有超时；生命周期见安装 Spec。
