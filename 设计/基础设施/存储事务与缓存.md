# 存储事务与缓存

## 采用与所有权

PostgreSQL 18 是两产品各自的正式事实库。采用 `pg` 8、Kysely 0.29.7、官方 `@dbos-inc/kysely-datasource` 5.3.0；持久工作由 DBOS 5.3 持有。LanceDB、数值资产及内存缓存是可重建服务材料，Blob 原件具有独立保留责任。共同身份、Selector、TimePoint、CallContext 与 Problem 直接使用[共同值合同](共同值与调用上下文.md)，精度沿[时间合同](时间与调度.md)。

`@nous-wave/platform/storage` 是普通库：提供连接、类型解析、事务适配、官方 datasource、迁移执行和关闭机械。Nous 与 Hept 分别创建实例、数据库和产品迁移；领域 owner 决定表、约束、索引、操作与事务。共享库不收集 Memory、World、Message 等业务表，也不维护业务任务或第二套 checkpoint。

本规范区分三件事：业务事实是否原子提交、工作能否恢复、实际外部效果是否已发生。它们分别由 owner 事务、DBOS 和效果 owner 的正式回执回答。

## 连接与迁移

共享工厂接受产品给出的 `Database` 类型、Pool 配置、迁移 provider、datasource 名称及 schema；返回本产品的 `db / datasource / close`。产品组合根只实例化一次业务 Pool/Kysely，领域直接取得所属事务的 client。

```ts
const db = new Kysely<Database>({
  dialect: new PostgresDialect({ pool }),
  plugins: [new CamelCasePlugin({ maintainNestedObjectKeys: true })],
});
const datasource = new KyselyDataSource('nous', db, 'dbos');
const result = await new Migrator({ db, provider }).migrateToLatest();
if (result.error) throw safeMigrationProblem(result.error);
```

`maintainNestedObjectKeys:true` 保留 owner JSONB 的原始嵌套键名。表/列命名转换不应改写模型输出、原平台 payload 或 JSON Pointer 所指字段。datasource 5.3 用 Kysely 构造器身份检查传入实例；当前 Node ESM/CJS 组合已遇到双构造器问题。工厂集中选用同一实际构造器并复用同一 Pool，不用隐含第二连接池绕开它。

迁移在接纳业务和恢复工作前执行，由产品显式注册，失败即停止该产品启动。DBOS 系统及 datasource schema 使用官方初始化/迁移 API。部署账号与运行账号分开：运行账号只获得所需表、sequence 和官方 datasource 权限。备份/恢复同时覆盖业务表、官方系统库、Blob 与必要密钥引用，恢复次序见[安装与生命周期](安装与生命周期.md)。

连接设置包含 `max / connectionTimeoutMillis / idleTimeoutMillis / statement_timeout / lock_timeout / idle_in_transaction_session_timeout / application_name`；默认值与无默认基础 schema 分开发行。两个产品、DBOS 系统连接与维护任务的总量必须在 PG 连接容量内。只读浏览与大规模批处理设置单次上限，不能占满业务连接池。

## 短事务与持久工作

| 操作 | 执行方式 | 成功依据 |
|---|---|---|
| 精确读、分页、短 CAS 修改、采用已保存候选 | owner 直接 Kysely 读/事务 | 正式对象与修订 |
| 同产品跨 owner 的原子采用 | 调用方组合普通函数，共用同一个 client | 一次 SQL commit |
| 等待模型/工具、长期调度、可恢复重建或多步效果 | 官方 DBOS workflow；每个业务采用步骤使用官方 datasource | DBOS 进度及 owner 正式事实 |
| 跨产品调用 | 官方 Client、稳定操作身份、接收方幂等操作 | 接收方完整回执 |

普通 owner 事务使用 `db.transaction().setIsolationLevel(...).execute(async trx => ...)`。既有事务通过明确私有参数/组合上下文传入；所有被调用 owner 使用它，不在内部另开独立事务。读后修改不能在两个互不相干的事务中完成。

workflow 中采用 `datasource.runTransaction(async () => { /* datasource.client */ }, {name})` 或 `registerTransaction`。业务写和该步骤结果在同一 PG 事务提交；必须每次取得当前 `datasource.client`，不提前捕获 base db。datasource 事务不能套在普通 DBOS step 或另一个 datasource 事务内。模型、网络、文件流、用户等待不持有 SQL 事务。[官方事务教程](https://docs.dbos.dev/typescript/tutorials/transaction-tutorial)、[datasource API](https://docs.dbos.dev/typescript/reference/datasource)。

官方durableCalls本身在DBOS step内执行。其Provider doX内的ModelInvocation接纳、dispatch和已知结果保全使用普通Kysely短事务，由长期调用gate处理checkpoint尚未保存时的恢复；此处不能嵌套datasource.runTransaction。离开该SDK step后的领域采用再使用workflow的官方datasource事务。ModelInvocation及原结果保全先于后续时间/语义回调，失败只继续原结果交接。

5.3 的 `readOnly:true` 不保存同样的 datasource 重放结果。需要冻结的决策输入应保存为该工作真实输入/结果；新外部派发前的当前权限检查仍重新执行。官方 datasource 只自动重试 SQLSTATE `40001`，退避从 1ms 按 1.5 倍增长至 2s；`40P01` 按 owner 的可重试语义处理，不假定 SDK 已覆盖。

业务 commit 成功后索引失败，正式对象保持成功。持久工作的父 workflow 恢复后续索引；普通短操作没有父 workflow，启动/官方scheduled reconciliation按owner真实变更cursor与已发布水位补齐，不能要求所有短修改先包workflow。已保存的模型成功输出在合同解析失败时仍可采用、查看和计费。任何错误都先在相应边界安全分类，再交 DBOS 保存，见[观测错误与诊断](观测错误与诊断.md)。

## 约束、并发与幂等

数据库约束表达实际不变量：FK、唯一业务身份、修订唯一、head 指针、非空和必要范围。CAS 用一条带 `expectedRevision` 的 UPDATE/INSERT；无返回行时读取实际 head，返回 owner 的 `revision_conflict` 和可披露的当前修订。

```sql
UPDATE memory_heads SET revision = $next_revision
 WHERE subject_id = $subject_id AND object_id = $object_id
   AND revision = $expected_revision
 RETURNING object_id, revision;
```

Kysely 使用 `.where(...).returning(...)`、`.onConflict(...)`、`.forUpdate()` 等真实 API。多行不变量先锁定固定顺序的 owner 行；涉及时间权威时沿 Clock → Subject/World → 对象顺序。仅有实际并发不变量需要时采用 serializable 或 `pg_advisory_xact_lock`；事务中不等待外部工作。

同库formed/observed等业务时间用`captureIn(tx,selection,operationId)`，和该正式事实一并提交；selection直接使用时间owner的domainId/preferClock合同，普通clock.read与查询预览只读。一个逻辑操作的不同step/observed/formed使用确定的phase子操作身份，同一phase恢复复用原ID；不同时间点不能共用一个capture key。跨库先以该子身份取得`clock.capture`最小回执，再进入本产品短事务保存完整回执及实际recorded。若本地事务失败，源高水位已推进仍合法；重试取得原capture而不改形成时刻。任何外部capture请求都在本地SQL事务外完成。

可重试 mutation 在其正式结果记录或所属 owner 的必要 receipt 中保存：操作身份、Subject/Consumer、操作种类、规范输入 digest、结果固定引用。唯一键按真实幂等范围建立。先查询原成功 receipt，再检查旧 expectedRevision；相同身份与相同输入返回原结果，不同输入返回冲突。重新调用时生成的新当前时间、默认配置或 provider 输出不能混入原请求 digest。

输入规范化使用稳定 JSON canonicalization 库并按 owning schema 选择字段；Ref 的 selector、嵌套对象顺序与十进制微秒必须规范化。直接 `JSON.stringify` 比较任意对象属性顺序会误判同一来源。权限校验和输出披露仍按当前 owner 规则执行。

DBOS datasource checkpoint 是恢复机械。独立 PG18 实验已观察到：业务写与步骤 checkpoint 同时可见、失败业务写回滚、安全 Problem 可恢复、同 workflow ID 不重复写；workflow 完成后官方清理 datasource checkpoint。因此长期幂等、正式回执与业务历史由 owner 保存，不能引用临时 checkpoint 代替。

两产品没有 2PC。发起方保存实际完整操作身份和冻结请求，接收方用原身份执行幂等操作；网络中断后查询/继续同一操作。`not_sent / unknown / completed` 由效果 owner 依据真实边界判定。unknown 进入其核实流程；不得生成新 ID 盲重做。只传完整领域操作，不导出内部事务函数。无需另建 outbox、重试表或跨库事务协调器。

跨产品根Task预算由Hept Task owner预留子额度。Hept在根Task锁内以稳定childOperationId创建`BudgetAllocationReceipt`，保存真实allocation Ref、rootTask Ref、受信Consumer/用途/允许职责、Money币种及上限、现实期限；同子身份同请求返回原分配，不同请求冲突。该owner的预留减少根Task可再分配额度。

Nous通过正式Client/受信绑定核验这份allocation，在本地按allocation锁定已用与未结预留，且同时执行Nous安装/Subject/Role限制。实际Provider费用只写Nous的ModelInvocation事实，Hept保存预算分配/结算及对应调用Refs，不复制第二份可改provider账目。完成后按原childOperationId与allocation回执结算并释放未用额度；unknown保留原预留，跨库响应丢失查询同一回执。Hept撤销或连接不可核验时停止新派发，已知结果继续保全；未确认完成/取消的额度不重新分给其他调用。币种不匹配拒绝执行，换汇必须是明确另项操作。此协议归Task与ModelInvocation两owner，无通用预算服务或跨库余额事务。

导出/恢复的预算闭包包含实际ModelInvocation、必要价目/用量事实、未结预留、BudgetAllocationReceipt及其引用；内容与秘密按授权选择。fork或更换安装保留原调用/分配作为历史来源，原issuer/target/Consumer/期限和金额不得由RefMap改成新的可用授权。新工作先由Task owner取得合法新分配；未决旧调用先按原来源核实。同一身份安装恢复也重新核验当前对端授权，恢复一个旧snapshot不会重新发放已经结算的额度。

## JSONB、时间、数值与查询

| 数据 | PG / Node / wire 约定 |
|---|---|
| 现实记录点和需要排序的时间 | `timestamptz(6)`；连接级 parser 返回精确字符串/微秒；禁止经 Date 往返 |
| 带时间域业务点 | owner 同时保存 domainId 与精确 at；比较遵循时间 owner，不直接跨域比较字符串 |
| 业务/配置/Clock revision | PG bigint；wire为正安全整数number，expectedRevision可用0表示初次；递增前检查安全范围，耗尽返回明确问题 |
| 无界cursor/bytes/计数 | PG bigint；内部BigInt；wire十进制字符串，不用Number窄化 |
| 费用/价格 | `numeric` 与十进制运算库；wire 精确十进制，不用浮点累计 |
| 领域 union 和原件结构 | JSONB；所属 Zod schema 解析；大整数在 JSON 内也保存十进制字符串 |

node-postgres 默认会把 timestamp/timestamptz 变为 Date，丢掉微秒；本轮隔离 PG18 读取 `...123456Z` 的默认结果实际为 `...123Z`。工厂使用 Pool/QueryConfig 的 `types.getTypeParser`，不修改跨产品的全局 parser。PG 输出固定 UTC 六位小数，具体规范化与 Temporal 运算沿时间 Spec。[pg 类型](https://node-postgres.com/features/types)、[PG18 时间类型](https://www.postgresql.org/docs/18/datatype-datetime.html)。

业务Pool在text模式对OID1184返回原始字符串，再由Temporal规范化；int8与numeric保持精确字符串。显式格式输出可用 `to_char(recorded_at AT TIME ZONE 'UTC','YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`。PG内部仍用时间类型排序/比较，格式化只在读取边界，不把所有时间改成任意JSON字符串。

所有 SQL 值通过 Kysely/pg 绑定。特别是 JS 数组默认可能作为 PG array 编码，JSONB 参数明确序列化并 `::jsonb`；查询字段、排序和 JSON 路径取 owner 白名单。JSONB GIN、表达式索引、普通 B-tree 根据实际过滤建，不给所有 union 字段盲加索引。[PG18 JSONB](https://www.postgresql.org/docs/18/datatype-json.html)。

分页采用 `kysely-paginate` 的 `executeWithCursorPagination`，显式 fields、稳定唯一 tie-breaker、encode/decode 和 `parseCursor`。同一 cursor 绑定 Subject、Consumer、purpose/audience、过滤、排序及历史视图；错用即 validation。时间排序使用精确值，不能把六位时间变为 Date 后写 cursor。分页先执行 owner 可见性过滤，再计候选配额；需要逐条后验时，续页 cursor 根据实际扫描位置前进。返回真正 `{items,nextCursor?}`。

批量 read/history/source 先去重固定引用，再用 `WHERE id = ANY(...)`、JOIN/CTE 或有界 IN 批读，恢复调用方顺序并逐项给实际结果。关系历史联用知识有效截点与实际观察/记录截点，不把多次公开 list 拼成全量表扫描。预算限制正文、源图节点、行数和 bytes，而不只限制首个请求的 limit。

## Blob 与文件边界

Blob 原件采用 `cacache` 的流和完整性 API。流程为 request Readable → 字节计量/上限 Transform → `cacache.put.stream`，由 Node `pipeline` 处理背压、取消与失败；默认单 Blob 64MiB，可按产品资源设置调整。流完成取得 integrity/bytes/mediaType 后，才向 DBOS/SQL 操作提交元数据。检查点不包含原文件字节。

重复上传凭据绑定原操作与持有者；相同内容复用 digest，不同 digest/bytes/type 冲突。文件完成而元数据事务失败会产生孤立字节，由有界清理回收；正式 Blob 行只在完整字节已有后建立。文件系统与 PG 没有共同事务，成功状态依照上述顺序。

读取先经实际Material/Media/DataArtifact/ImportArtifact等持有者owner检查当前scope、policy、祖先传播和保留状态，再使用`cacache.get.stream.byDigest`。HTTP byte Range是物理传输范围，语义区域仍用正式Selector，包括node.pointer和media.startUs。知道digest不授予读权限。解析、派生和发布沿[媒体与材料基础](媒体与材料基础.md)，数据包的正式持有者沿[数据生命周期](数据生命周期与发行.md)。

空安装的导入使用安装级`data.uploadImportArtifact`，`POST /v1/import-artifacts`接标准流，沿同一Blob机械返回`{artifactRef:Ref,digest:string,bytes:string}`；`data.importPreview`接收该`artifactRef`。此处scope不依赖既有Subject，权限为明确数据导入范围；包限额1GiB，未被计划引用的ImportArtifact默认24小时过期。导入计划的保留引用、取消与清理由数据owner管理；媒体64MiB默认限额继续作用于媒体入口。

`cacache.rm.entry` 只删除索引，内容仍可按 digest 读；`rm.content` 才移除共享字节。物理删除前查询本产品仍保留的合法持有者。`verify` 会回收未被索引引用的内容，不能在权威 Blob 目录里把丢失索引的正式 Blob 当可随意删的缓存。原件、可重建表示和临时缓存使用不同目录/清理政策。[cacache 官方 API](https://github.com/npm/cacache)。

## Serving、缓存与清除

文档 FTS/dense 统一采用 LanceDB；原 Native/VCP 数值、内部图与 concept/EPA/candidate ANN 由同进程 Rust 数值 addon 保存可重建资产。具体资产 identity、space/producer、staging/publish、增量 cursor、读句柄和删除依赖见[检索服务](检索服务与认知消费者.md)。PG 只保存已发布指针/manifest 和正式变更事实，DBOS 保存构建进度；不添加自有队列、lease、工作状态或 Redis 服务。

内存缓存采用成熟有界 LRU，实现机械由 owner 直接配置。key 包括安装/Subject、固定输入、时间视图、owner cursor、space/producer/config 修订；当前权限不靠无版本 TTL 正向缓存。资源句柄按 AssetSet 代际持有，查询结束释放；发布新代后旧读不会切到半个新集合。

清除先在 owner 事务收紧可用性/传播并保存真实受影响引用，当前读取立即生效；后续工作删除 serving 行、support、向量、缓存、派生 Artifact 和无人持有的字节。清除流程显示尚未删除的实际路径及备份保留期限。源撤权时，索引和缓存不能继续保留其私密影响供查询使用。

包含未结预算/外部效果的清除先关闭新派发，再由实际owner结算、释放或保留最小unknown回执。Task或DBOS历史的删除不能级联丢失ModelInvocation、allocation和原效果幂等身份；正文/输入可以按政策清除，尚需核实的无正文引用与预留作为真实pending报告。ExportSelection只提供字节保留引用；当前导出授权失效或purge包含该来源时，由数据owner停止相应导出、关闭其Artifact并释放临时引用，再执行共享字节回收。

磁盘/内存/Pool 压力使用 `resource_pressure`，带资源与实际可恢复条件；停止接纳相应重建/上传工作，已完成正式事实保持可查。退出时停止新接纳，保存实际效果，等待有界在途事务，关闭 DBOS 后销毁业务 Kysely/Pool；缓存、Lance/Rust 句柄和文件流各由实际持有者关闭。

## 施工验证

复用一条真实场景：接纳输入/流式 Blob → 实际调用 → 认知采用 → 查询与历史 → 撤权 → 清除；穿插同 ID 重试、CAS 冲突、微秒 cursor、嵌套键和大整数。必要规则验证事务业务/checkpoint 同提交、失败回滚、已成功外部结果重放及数据库恢复。库自身算法和薄转发不另造测试框架。
