# 小团队协作约定

Architecture Vault 服务于三人团队和 AI Agents，不是审批系统。

## 基本规则

- 任何成员都可以直接修改文档。
- 重要内容通过普通 Git review 发现问题，不设专门审批角色。
- 文档允许不完整，但必须明确当前结论与开放问题。
- 讨论得到更好结论后直接改正文；Git 历史保存旧观点。
- 不为小决定写 ADR，不维护需求追踪矩阵。
- 同一事实只保留一个主要说明位置，其他文档使用链接。

## 文档状态

只使用四种状态：

- `idea`：未经整理的方向；
- `draft`：已经形成可讨论内容；
- `active`：当前共同采用；
- `archive`：已失效，只为历史上下文保留。

状态不是审批结果。没有必要给所有文档添加 frontmatter；只有状态容易误解时才标注。

## 什么时候写 Decision

只有同时满足以下条件才记录：

1. 影响多个模块或长期数据；
2. 存在合理替代方案；
3. 未来成员很可能追问原因；
4. 改变它会造成明显迁移或兼容成本。

Decision 只回答：背景、当前选择、原因、代价、重新考虑条件。

## 收件箱

新想法、对话摘录、外部资料和未定问题先进入 `07-Inbox/`。任何人都可以直接整理到正式主题文档；不需要等待定期归档会议。

## 更新责任

修改代码或设计时，更新最接近事实的文档：

- 当前实现变化：`00-Start/Current-State.md` 或 `04-Engineering/`；
- 系统边界变化：`02-System/`；
- 概念模型变化：`03-Concepts/`；
- 长期选择变化：`05-Decisions/`；
- 实验结果：`06-Research/`。

## 文风

- 先写结论，再写原因。
- 使用具体名词和数据流，避免宏大但不可执行的表述。
- 区分“当前实现”“目标设计”“研究猜想”。
- 不复制代码文档中已经精确描述的实现细节；链接到代码仓库即可。
- 文档应能被独立切片给 AI Agent 阅读，避免只靠隐含上下文。
