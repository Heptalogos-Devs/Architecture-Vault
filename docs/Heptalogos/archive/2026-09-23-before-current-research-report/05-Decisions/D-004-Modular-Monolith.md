# D-004：模块化单体优先

## 背景

Heptalogos 包含交互、认知、记忆、任务、能力和控制面等多个领域，但当前是三人研究团队，负载、故障域和部署需求尚未证明需要微服务。

## 当前选择

早期采用模块化单体：

- 清晰的领域所有权和端口；
- 可以在一个运行时或一台机器上部署；
- 可靠交接依赖数据库和持久契约，不依赖共享内存假设；
- 只有平台 SDK、权限、原生执行或独立故障域成立时拆 Worker 或进程。

## 原因

- 降低构建、部署和观测成本；
- 跨领域修改容易保持一致；
- SQLite 事务足以支持早期负载；
- 服务边界可以由数据所有权先行验证；
- 避免将语言偏好误当作系统边界。

## 约束

- 模块不得跨库或跨 Repository 私自修改其他模块数据；
- 外层实现内层端口；
- 核心领域不导入平台或模型 SDK；
- 长期副作用通过命令和事件显式表达；
- 合并部署不等于合并权威。

## 代价

- 单进程故障可能影响多个角色；
- 需要主动维持模块边界；
- 部分 Worker 的资源隔离有限。

## 重新考虑条件

- 独立伸缩或资源隔离成为真实需求；
- 平台 Adapter 故障频繁影响核心；
- 团队所有权形成稳定边界；
- 发布和升级周期需要独立；
- 测量证明单运行时吞吐或可靠性不足。
