# 文档职责与权威

## Architecture-Vault

Architecture-Vault 保存跨仓库、长期有效的设计知识。

### 目标设计

回答系统应当是什么。内容包括领域职责、核心对象、对象关系、权威、不变量、跨系统协作和已经确定的目标物理结构。

目标设计不记录当前代码、文件路径、缺陷清单、施工顺序、历史设计和仓库迁移状态。

每个系统范围声明自己的唯一直接编辑来源。Heptalogos 的目标设计正文由 `docs/Heptalogos/TARGET_DESIGN.md` 维护，Nous Wave 的目标设计正文由 `docs/Nous-Wave/TARGET_DESIGN.md` 维护。PDF、HTML 或其他发布物只能从这些来源派生，不能加入 Markdown 中不存在的设计语义，也不形成并行 Authority。其他系统继续遵循各自范围的来源声明。

### 设计决定

记录已经确定的结论并指向目标设计和论证。决定索引保持简洁，不复制整段正文。

### 设计论证

记录方案比较、选择理由、失败模式、外部研究依据和设计后果。论证用于解释目标设计，不覆盖目标设计。

### 研究

保存实验、算法候选、外部资料和仍需验证的技术问题。研究结论只有经过设计决定后才进入目标设计。

### 跨系统合同

保存 Heptalogos 与 Nous Wave 之间长期有效的语义分工，例如主体身份、认知输入、主动追求、行为结果和证据回传。

## 代码仓库

Heptalogos 与 Nous-Wave 各自保存与代码同步变化的工程知识：`AGENTS.md` 与工程治理、当前实现架构、当前状态与差距、活跃计划和路线、可执行规格、依赖决定、资格记录和包级文档。

长期目标设计只链接到 Vault，不在代码仓库复制一份。

## 权威顺序

对产品语义和领域设计：Vault 目标设计 → Vault 已接受设计决定 → 当前代码仓库的可执行规格 → 当前计划 → 当前实现。

跨系统交互语义由 `docs/integration/` 的合同唯一维护。系统目标设计可以说明各自承担的边界义务，但应以该合同为准并保持同步。

对工程执行规则、依赖和资格结论，由代码仓库自己的治理文件、依赖决定和资格记录负责。

## 历史

Git 历史保存已淘汰的设计和旧文档。活动目录只保存当前有效知识，不建立第二套历史归档文档树继续占据阅读路径。
