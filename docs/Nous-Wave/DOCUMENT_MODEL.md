# Nous Wave 文档模型

## 1. 文档层级

Nous Wave 的设计资料分为六类。每一类回答一个不同问题。

| 层级 | 回答的问题 | 是否规范性 | 允许包含的内容 |
|---|---|---:|---|
| **目标设计** | 系统最终应当是什么？ | 是 | 领域、对象、语义、边界、不变量、目标物理架构 |
| **设计决定索引** | 哪些设计已经确定，详细定义在哪里？ | 是，索引性质 | 简短结论、状态、目标设计位置、论证链接 |
| **设计论证** | 为什么这样设计？其他方案有什么问题？ | 否 | 方案比较、推导、反例、外部研究、设计后果 |
| **研究与实验** | 证据实际支持什么？ | 否 | 实验设置、公式、数值、软件快照、文献 |
| **当前状态与审查** | 代码现在是什么？与目标差多少？ | 否 | HEAD、文件路径、缺陷、迁移、资格结果 |
| **计划与规格** | 接下来怎样把目标设计落实为代码？ | 执行期规范 | 顺序、依赖、接口/数据模式/事务/测试/验收 |

## 2. 目标设计 PDF

`main.tex` 及其生成的 `Nous_Wave_Target_Design.pdf` 是长期目标设计的正式载体。

正文只陈述已经进入目标设计的内容：

- 系统定义与适用范围；
- 领域所有权；
- 核心对象和对象之间的关系；
- 权威、运行时和服务投影边界；
- 证据、修订、时间和生命周期语义；
- 查询、持久化和跨系统集成不变量；
- 已经确定的目标物理架构。

PDF 不记录：

- 历史设计和“重新设计”叙事；
- 方案比较和“为什么”；
- 外部论文综述；
- 算法实验结果；
- 当前代码基线；
- 文件路径和代码缺陷；
- 中期检查施工计划；
- 尚未形成设计结论的问题。

如果某项内容尚未确定，目标设计只写已经确定的边界。例如，动机领域必须与 Heptalogos 的行为承诺分离；具体目标生命周期尚未冻结，则由 `OPEN_QUESTIONS.md` 和后续可执行规格处理。

## 3. 设计论证

`rationale/` 保存设计决定的推理过程。这里可以完整回答：

- 有哪些可行方案；
- 各自承担什么语义；
- 哪些方案会产生歧义或不良反馈；
- 为什么当前决定具有更低的长期工程成本；
- 哪些数学模型只是参考实现；
- 设计决定会约束哪些下游可执行规格。

论证文件不能覆盖目标设计。发现论证和目标设计不一致时，应先重新做设计决策，再修改目标设计与决定索引。

## 4. 研究与实验

`research/` 保存可复核证据。实验结果必须包含问题、条件、结果和适用范围；不能从局部数学一致性直接推出系统级检索质量。

算法实验可以改变后续默认实现，但只有当实验结果上升为设计决定时，才修改目标设计。

## 5. 当前状态、审查和计划

`CURRENT_STATE.md` 只描述当前实现状态。`audits/` 记录更具体的实现差距和缺陷。`plans/` 根据目标设计和当前状态安排施工。

它们之间的关系为：

```text
目标设计 ───────────────┐
                        ├─→ 实施计划 → 可执行规格 → 代码 → 验证
当前状态 / 实现审查 ────┘

研究 / 实验 → 设计论证 → 设计决定 → 目标设计
```

## 6. 下游代码仓库

Architecture-Vault 保存跨项目的长期目标设计和研究资料。Nous-Wave 代码仓库维护当前执行期的架构、设计决定、实施计划、可执行规格、资格记录和代码真值。

当目标设计发生实质变化时，应先更新 Vault 的目标设计与设计决定，再在代码仓库中产生新的执行期架构与可执行规格。当前实现不得因为已经存在而获得目标语义上的优先权。
